# Retire — land, close the workspace and worktree, update main, log the outcome

Helper: `sh "${CLAUDE_PLUGIN_ROOT}/scripts/herdr-tools"`, written `herdr_tools.py` below; it runs the helper with the first Python 3.9+ it finds (`python3`, `python` or `py -3`). It refuses to run outside a Herdr pane. This skill merges, destroys a workspace and a worktree, and updates the main checkout, so it always confirms first. It works the same on every project; the project's profile (`herdr_tools.py profile --path <main checkout>`; `retire-info` names it) supplies the forge, tracker, worktree commands and dev server.

1. **Gather.** Run `herdr_tools.py retire-info <agent, workspace id or label>`. It refuses a main checkout and this session's own workspace, and prints JSON: workspace, worktree, main checkout, branch, MR, the agent's parsed status report (`report`, from `report_path`) and `checks`. Show every check with its detail. The MR is the worktree branch's; when that branch has none, it is the first one the report's `mr:` line names, which may be in another repo (an agent in one checkout can open its MR in another). `mr.ref` (`group/project!iid`) is then set, and the worktree, branch and head checks are about the agent's own checkout, not that MR's repo. The `head` check passes when HEAD is the merged commit, is on the default branch, or carries the same patch as the squash or merge commit (`land` rebases an MR that is behind, so the merged commit is usually not HEAD); its detail says which.
2. **No report?** An agent spawned with `spawn.brief: false` keeps none, and the `report` check says so and passes: skip this step. Agents spawned before status reports existed have none. If the agent is still running, ask it with `/herdr:ask`, waiting for the reply: "Write your status report to `<report_path>` in the format of the Status report section of `${CLAUDE_PLUGIN_ROOT}/skills/spawn/references/brief-template.md`, then reply done." Then re-run `retire-info`. If the agent is gone, draft the summary yourself from `glab mr view <iid>` and label it "reconstructed".
3. **Land or stop.**
   - **The repo merges (`land: repo` in `retire-info`):** never land from here; `land` and `watch` refuse anyway. If the MR is open, say it waits on the repository's own process, with the MR link, and stop. If it is merged, go on, with no merge in the confirmation.
   - **Ready to land:** the MR is open, `merged` is the only failing check apart from `safe_to_retire: no` given *only because the MR is open*, the report has no open questions, and the user has validated the work (ask if they haven't said so). Then this run lands it: show the MR, its head commit and pipeline status, and include "squash-merge !<iid>" in the confirmation below. Never land on a failed or missing pipeline, a draft, conflicts, unresolved threads or a missing approval; `land` refuses those anyway.
   - **`approved` fails:** the MR needs an approval from someone other than its author. Say so with the MR link and who could approve it, and stop; landing waits for the approval, never works around it.
   - **Any other failed check:** show the report's Summary, Open questions and Follow-ups, say what blocks retirement, and stop. A merge that did not happen or a HEAD with commits the merge did not take means work would be lost: go on only if the user explicitly says to discard it.
4. **Find the workstream**, only when the `/work:` skills are available; otherwise skip steps 4 and 5 and the checkpoint in step 7 without mentioning them. Run the work plugin's `work.py find --cwd <main_checkout>` (the `/work:checkpoint` skill names the helper's path; the worktree path never matches, its main checkout does). If several match, ask which. If none matches, skip the work-store steps.
5. **Draft the log entry** for a match, unless the workstream's Log already records this work (an agent that retired its own worktree often checkpointed too): one Log line, `- <today> · <KEY> merged as MR !<iid> (<mr url>): <Summary in one line>. Follow-ups: <Follow-ups, or none>`, and a new `next` only if the report makes the current one wrong.
6. **Confirm once** with the user: the merge (when landing), the workspace label, worktree path and branch to remove, closing the ticket (when the profile has a tracker), the drafted Log line and `next` for `<area>/<slug>`, and the follow-ups you will capture (step 8) with their proposed priority. They may edit the draft.
7. **Retire**, in this order:
   - **Land** (when confirmed): `herdr_tools.py land <agent>`, which lands the MR `retire-info` found, in whichever repo it is. For any other MR, or one the report doesn't name, pass it: `herdr_tools.py land --mr <url or group/project!iid>`. Through the forge (GitLab or GitHub) it rebases the MR/PR if it is behind, waits for the head pipeline or checks, and squash-merges pinned to that commit. It deletes only the remote branch (GitLab's "delete source branch"; on GitHub, through the API: a branch that is already gone counts as deleted, a failed delete is retried once, and only a second failure is a warning); the local branch and the worktree stay for the steps below. Once the merge succeeds, nothing after it fails the land: if GitHub can't be read back after a retry, `land` prints a warning and reports the PR merged with its commit unknown (`retire-info` reads the commit from the forge later). Expect a wait of a pipeline's length after a rebase; report progress. If it refuses, stop and show the reason. To land several agents in an order the user gives, run `herdr_tools.py land <agent> <agent>...` in the background (`run_in_background`): it lands each in turn, asks a conflicting agent once to rebase and retries it after the others, and prints one line per agent; then retire each merged agent from step 7 on. To land several as each becomes ready, run `herdr_tools.py watch <agent>...` in the background instead: it lands the first whose report says "ready to land", asks a conflicting agent once to rebase, keeps waiting on a missing approval, and exits; then retire that agent from step 7 on.
   - `herdr workspace close <workspace_id>` (ends the agent in it).
   - Remove the worktree with the profile's `worktree.remove` (`worktree_remove` in `retire-info`) if it has one, else `git -C <main checkout> worktree remove <path>`. Never use `--force`. Skip this when `worktree_removed` is true (the agent may have cleaned up after itself); run `git -C <main checkout> worktree prune` instead.
   - With `branch_cleanup: repo`, that command owns the worktree and the branch: if it refuses or fails, show its output and stop, and skip the fallback below and the branch deletion. Its checks are the point, so working around them is not cleanup.
   - Otherwise, if the repo's command fails or leaves the worktree in `git worktree list`, remove it by the `worktree` path from `retire-info`: `git -C <main checkout> worktree remove <path>`. Repo commands often derive the folder from the branch name, which misses when the agent moved the worktree to a follow-up branch.
   - Unless `branch_cleanup` is `repo`, delete the local branch only when its MR is merged and the branch still exists: `git -C <main checkout> branch -D <branch>`. When `mr.ref` is set (the MR is in another repo), the agent's branch had no MR of its own: delete it only if its commits are on its own default branch or the user says to discard them. When the agent moved to a follow-up branch, also delete the ticket's earlier local branch, but only if its tip is the head commit of a merged MR (`glab mr view <iid> -F json` → `sha`; on GitHub `gh pr view <number> --json headRefOid`). Leave the remote branches to `land`, which deleted the merged one on either forge.
   - Close the ticket when confirmed and the profile has a tracker: for `jira`, move it through `tracker.done_path` one state at a time (`acli jira workitem transition --key <KEY> --status "<state>" --yes`) and read the status back.
   - **Update main:** `herdr_tools.py update-main --path <main checkout>`. It restores files that differ from HEAD only by JSON key order (Claude Code rewrites settings that way), refuses on any other local change (show it; never discard it), and fast-forwards. Then:
     - `restart_needed` empty: no restart (most dev servers reload code changes on their own).
     - `restart_needed` lists files: if `herdr_tools.py main-server status --path <main checkout>` shows a pane, run `main-server restart` and report `ready`; otherwise tell the user which files need a restart, and offer `main-server start` when the profile has a `dev_server` (stop any dev server they run in their own terminal first; it holds the port).
   - **Keep copies outside the repo true**, from the same `update-main` result:
     - The profile has `mirrors`: run `herdr_tools.py sync-mirrors --path <main checkout>`. Report each `synced` copy with its backup, and each `problem` (a missing file or marker line): it was left as it was, so tell the user.
     - `facts_changed` lists files: the merge changed something the planning page restates (`planning.facts` says which sections). Refresh those sections from the main checkout, taking test counts from the default branch's latest pipeline, not memory. Then check, publish and verify as in step 8's **Capture**.
   - Run `/work:checkpoint` for the matched workstream with the confirmed Log line and `next`; the user already approved them, so don't ask again.
   - Leave the status report file; the next agent with that name overwrites it.
8. **Capture follow-ups** so no valid task is lost. `retire-info` lists them in `followups`: each Follow-ups bullet and each change the agent marked Unverified. When retiring several agents, triage them together.
   - **Check each is valid:** still true on the default branch now (another merge may have fixed it; look at the code), not already ticketed (search the tracker), and real work rather than a note. Drop the rest, saying why. Fold device or environment checks that wait on the same blocker into one item.
   - **Duplicated concepts:** whatever its report says, check whether the merged work introduced a rule, threshold, mapping or value set that is also defined elsewhere (search for its values and names). A duplicate is a fast follow that names one owner.
   - **Size it** (S: under a day; M: a few days; L: more) and **prioritize it against the planned work** in the profile's tracker and planning page:
     - **Fast follow** (spawn soon): small items that fix a latent bug, a flaky or misleading test, wrong config, a security or data-loss risk, or a refactor that prevents errors later. Cheap now, costly once forgotten or built upon.
     - **Next:** items that unblock or de-risk planned work, or keep a pattern consistent while it is new.
     - **Backlog:** larger improvements and polish, prioritized by impact; verifications that wait on a blocker are linked to it.
   - **Capture:** with a tracker, create a ticket per valid item (in the profile's `tracker.project`, under `tracker.parent` when set, priority set, unassigned unless it is the user's call), linked to the ticket it came from; read each back. Write acceptance criteria against a shared concept's owner (file and export), never by restating its values. Without a tracker, add it to the workstream's next steps. With a `planning` page in the profile, add the items to it in priority order: read the published page first, edit, run `planning.check` on the edited copy (when set) before every publish, however small the edit, then publish. Read the live page back and run the check on it too, then sync `planning.local_copy`. A single unescaped quote in a page's script can blank the whole page.
   - **Tell the user**, per item: what the issue is, why it matters, its size and priority and why, and the ticket. Offer to spawn the fast follows. Ask before creating tickets only when an item's validity or priority is a real judgment call; include them in the step 6 confirmation when known then.
9. **Report** what was merged, closed, removed, updated, logged and captured.
